## 标题

```
[bug] 第三方插件写入的 session event 会让会话永久打不开——两条逃生口都不对插件开放
```

---

## 正文

### 一句话

第三方插件调 `session.append` 写自己的事件类型之后，**那个会话就再也打不开了**——不是少几行，是整份日志被拒绝解释。而 dsh 为这种情况准备的 `ignorable` 标记，插件恰恰没有任何办法设上。

版本：`0.1.0-rc.8`。

### 最小复现

一个十行的插件：

```ts
// index.ts
import type { Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/dsh-session/types' {
  interface SessionEventMap {
    'demo/hello': { version: 1 }
  }
}

export const name = 'demo'
export const inject = ['agents']

export function apply(ctx: Context): void {
  ctx.on('agent/session-start', ({ agent }) => {
    agent.session.append('demo/hello', { version: 1 })
  })
}
```

装上、开一个会话（`agent/session-start` 就会写入，不必发消息）、**重启 dsh**，
再打开那个会话：

```
history unavailable for session "session-…": SessionFormatUnsupportedError:
session "session-…" contains event type "demo/hello" (seq 4) unknown to this
harness and not marked ignorable; refusing to interpret the log — it was likely
written by a newer harness
```

那个会话此后再也打不开——**包括插件仍然装着的时候**（已实测：上面那段错误就是这么来的，
demo 插件全程在 `bundles` 里）。

⚠️ **重启那一步不能省。** 会话还在内存里时读的不是持久化路径，刷新页面看起来一切正常；
要等进程重启后从磁盘恢复，`assertEventsSupported` 才会拒绝。这也是它在真实使用中的样子:
写入那天没事，第二天打不开了。

### 机制

拒绝发生在 `packages/session/session-persistence/src/coordinator.ts` 的
`assertEventsSupported`：

```ts
if (KNOWN_SESSION_EVENT_TYPES.has(event.type) || event.ignorable === true) continue
throw this.unsupported(meta, `… unknown to this harness and not marked ignorable; …`)
```

两个条件对第三方插件都不成立：

**① `KNOWN_SESSION_EVENT_TYPES` 是生成的**，`packages/core/session/src/known-event-types.ts`
的文件头写着 `GENERATED by scripts/gen-persistence-catalog.ts`，内容是「Every
`SessionEventMap` member **declared in this repository**」。仓外的类型按构造就在集合外——
这一点该文件自己也说了：

> Downstream (out-of-repo) plugin events are outside this list by construction; a
> registration surface for them is deferred until such a consumer exists.

**② `Session.append()` 不接受 `ignorable`。** 它自己构造 envelope
（`packages/core/session/src/index.ts`），可选参数位是
`T extends SurfaceEventType ? [opts: SurfaceIntent] : []`，而 `SurfaceIntent` 里只有
`sourceEventSeqs` 与 `surfaceOp` 会被取出。写入方没有任何途径把 `ignorable` 放上去。

所以那句「deferred until such a consumer exists」的 consumer 已经出现了：
[`dsh-swarmdrop`](https://github.com/swarm-apps/dsh-swarmdrop) 用 session event 承载传输行
与 `@` 引用候选——这正是事件溯源该有的用法（对话行必须能从日志逐字重建），而不是绕开它。

### 我们的临时缓解，以及它为什么不够

插件在加载时把自己的四个类型 `add` 进那个 `ReadonlySet`（运行时它是个真 `Set`）。
两个修不了的地方：

**a) 卸载插件之后，那些会话仍然打不开。** 我们只能在 README 里写「要停就 disable，
别 uninstall」——对一个用户随时会卸的插件来说，这是很糟的建议。

**b) 它依赖插件与 dsh 解析到同一个 `@deepseek-ai/dsh-session` 模块实例。**
普通安装成立；**dsh 从源码 checkout 用 `tsx` 跑时不成立**——两边拿到各自的模块图。
实测（同一进程内加探针）：

```
[plugin]      before 48  →  after 52   has('swarmdrop/sent') = true
[coordinator] known size 48            has('swarmdrop/sent') = false   ← 每次都是
```

改一个模块级常量本来就不该是插件该做的事，这只是当下唯一能做的。

### 想请教的方向

不敢替维护者定方案，列几个我们想到的，以及各自的顾虑：

1. **给 `append` 一个可选的 `ignorable`。** 最直接。顾虑是它会出现在每个调用点的签名上，
   而仓内事件一个都不需要它。
2. **在 `SessionEventMap` 的声明合并处表达。** 插件声明类型时就说明它是可跳过的，读路径
   查这份声明。类型层面最干净，但需要一个运行时可查的形态。
3. **一个运行时注册面**（`ctx.sessions.registerEventType(type, { ignorable: true })`），
   也就是 `known-event-types.ts` 里说的那个「registration surface」。
4. **按前缀放行**：带命名空间前缀的类型默认 ignorable。改动最小，但把「可不可跳过」
   绑在命名习惯上，不如前三个显式。

无论走哪条，我们都想确认一件事：**「一个仓外插件写下的事件不应该让整个会话不可读」是不是
你们认可的目标**。如果是，我们很乐意按你们定的形状去适配（也愿意写文档或做验证）。

### 附带一个小的观察

`packages/extensions/ui-cordis/README.md` 说自己的面板挂在 `shell.overlay`，但
`src/client/index.ts` 与生成的 slot catalog 一致指向 `sidebar.footer.action`
（`shell.overlay` 在 catalog 里的 occupants 是空的）。我们照着 README 找了一圈才发现——
如果对得上，顺手更正一下会省下后来人的时间。
